# 3 GB 引擎基準測試

2026-10-29，v0.4.0 重新測試同一份 `dist/core.js`、`dist/relations.js`，以 Node Worker 與真實檔案系統介面替換瀏覽器 OPFS。這驗證解析／索引的演算法與磁碟讀寫路徑，**沒有驗證瀏覽器 OPFS、File.stream、gzip 或 Canvas 的時間、記憶體、FPS**。

| 項目 | 結果 |
| --- | --- |
| JSON 輸入 | 3,000,583,032 bytes（約 3.00 GB，非 GiB） |
| 事件 | 2,932,637 筆 X 事件、8 軌道 |
| Args 分布 | 每事件約 900 bytes 字串，另有索引欄位；每 25 筆帶 address |
| 輸入順序 | 依 ts 遞增；合成資料，非使用者真實 trace |
| 關聯鍵 | 117,306 筆 |
| 解析＋索引＋fsync | 40.66 秒 |
| 吞吐量 | 73.79 MB/s（含合成輸入生成成本） |
| 程序 RSS 峰值 | 344.17 MB（主程序與 Worker 合計，非瀏覽器記憶體） |
| 索引與事件磁碟量 | 3,190,031,386 bytes |
| 冷應用快取查詢 | 中位數 6.26 ms，P95 59.18 ms |
| 熱應用快取查詢 | 中位數 4.39 ms，P95 52.73 ms |
| Address 查詢 | 1.56 ms，顯示 14 筆候選 |
| 主執行緒計時器額外延遲最大值 | 13.14 ms（20 ms 週期，不是 FPS） |

查詢共 80 個視窗、每次 8 軌道、寬度 1,200 像素，交錯全範圍、1/10、1/100、1/1000 範圍。冷查詢清除應用層的 24 塊讀取快取，**未清除 OS 頁面快取**。P95 為排序後第 floor((N−1)×0.95) 個數值。

硬體：Intel Core i5-10400 2.90 GHz、12 邏輯 CPU、34.24 GB OS 回報 RAM；Windows x64，Node v24.22.1。磁碟介面使用同步檔案 I/O，測試檔在系統暫存資料夾；磁碟型號未記錄。

原始數據與受測來源 SHA-256：[benchmark-2026-10-29-v0.4.0.json](benchmark-2026-10-29-v0.4.0.json)。腳本：[benchmark.mjs](../scripts/benchmark.mjs)。如解析器或索引改變，必須檢查雜湊與重跑受影響的基準，不能以版本號當作相同來源的證明。

未涵蓋：高密度微小事件、每事件唯一名稱、大量軌道、巨型單筆 args、完全逆序事件、大量位址鍵、gzip 解壓縮、真實瀏覽器儲存配額及渲染。這些形狀可能有顯著不同的效能，初版不把單次合成測試宣稱為「任意 3 GB trace 都快速」或「快於 Perfetto」。

下一輪瀏覽器驗收應在桌面 Chrome / Edge 以同一來源 commit 量測首次匯入、快取還原、峰值記憶體、平移／縮放 p50/p95 延遲、長任務與 address 查詢，並使用實際 trace。

初版紀錄仍保留於 [benchmark-2026-10-29.json](benchmark-2026-10-29.json)。v0.2.1 未命名事件補名的紀錄也保留於 [benchmark-2026-10-29-v0.2.1.json](benchmark-2026-10-29-v0.2.1.json)。本次 v0.4.0 加入短 TID 補名與 Args 分析，修正末端點樣本的半開範圍，再次量測匯入與查詢，但仍不是瀏覽器實測。單次查詢延遲會受 OS 快取與系統負載影響，不以不同時次的單一結果宣稱效能提升。

## 100 萬筆 counter 專項

同一環境、同一份 v0.4.0 核心，另產生 1,000,000 筆 C 事件、4 條數值曲線，JSON 共 94,702,287 bytes。一般值是小於 1 的連續變動，定期加入正／負 12,345 尖峰。80 個查詢交錯全範圍、1/10、1/100、1/1000，寬度 1,200 畫素；每個查詢的最大與最小值都與原始數據重新計算核對。

| 項目 | 結果 |
| --- | --- |
| 解析＋索引＋fsync | 5.31 秒 |
| 程序 RSS 峰值（採樣） | 356.80 MB |
| 事件及固定寬度索引 | 157,702,286 bytes |
| Manifest | 2,998,402 bytes |
| 冷應用快取查詢 | 中位數 10.08 ms，P95 18.37 ms |
| 熱應用快取查詢 | 中位數 9.91 ms，P95 21.16 ms |
| 最大傳回節點數（4 軌道合計） | 18,593 |
| 範圍極值核對 | 80／80 符合 |

摘要每個索引區塊至多 32 個時間桶，各保留首尾與最大／最小樣本，以緊湊數字 tuple 儲存。僅在摘要時間跨度不大於一個畫素、且完全落在視窗內時使用摘要；跨視窗邊界與放大後讀取確切索引。最終每條軌道每畫素最多四個代表樣本，並可額外回傳左右各一個相鄰樣本作為繪圖裁切脈絡，不把插值當作事件。輸出仍是解析度聚合，不能視為每筆樣本都有獨立像素；放大可查看原始資料。

粗摘要不回報虛構的精確每畫素樣本數。原始索引的逐筆讀取使用固定暫存槽，避免因一個視窗建立百萬個完整物件。這是 Node 引擎的 counter 測試，輸入約 95 MB，**不是 3 GB counter 或瀏覽器的驗收**；RSS 包含測試主程序與 Worker，不是瀏覽器記憶體。

原始數據：[counter-benchmark-2026-10-29-v0.4.0.json](counter-benchmark-2026-10-29-v0.4.0.json)。重播：`node scripts/benchmark-counters.mjs 1000000`。輸入與索引檔在系統暫存目錄產生，完成後移除；只保留數據紀錄。
