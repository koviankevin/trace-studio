# 3 GB 引擎基準測試

## v0.8.0：瀏覽器更新延遲

新增可手動開關的本機效能記錄，不設輪詢計時器，不記錄檔名或事件內容。從範圍／軌道狀態更新開始，包含 25 ms debounce、佇列、Worker 查詢與主頁 Canvas 提交；尚未經過匹配查詢回覆的舊畫面不會被算成完成。只計最新狀態的完成樣本，連續操作被合併的更新與背景分頁略過另行計數。P50／P95 用最近最多 512 筆的排序後第 floor((N−1)×p) 筆。

Windows 內嵌 Chromium 156、瀏覽器回報 visible、1280×720；從本站 OPFS 還原已保存的 3,000,583,032 bytes／2,932,637 筆 X 事件／8 軌道合成 Trace，沒有重新解析原檔。先全覽，再交替放大／縮小 15 組；另一輪先放大一次，再交替 D／A 平移 8 次並等動畫尾端完成。完整時間樣本、上下文、來源 SHA-256 與可重算摘要見 [runtime-browser-2026-10-29-v0.8.0.json](runtime-browser-2026-10-29-v0.8.0.json)。

| 項目 | 縮放 | 鍵盤平移期間（含初次放大） |
| --- | --- | --- |
| 完成 Canvas 更新 | 30 筆 | 21 筆 |
| 被合併的狀態更新 | 0 | 17 |
| Canvas 更新 P50 / P95 / 最大值 | 53.2 / 66.2 / 83.5 ms | 56.3 / 67.7 / 70.1 ms |
| Worker 查詢 P50 / P95 | 4.3 / 7.3 ms | 4.1 / 5.6 ms |
| 主頁長任務 | 0 次 | 0 次 |

這不是 compositor 呈現、實體按鍵起點、FPS 或 INP 的量測；被合併的輸入沒有各自完成畫面。樣本數有限，快取為熱，資料形狀單一，不能保證任意 3 GB Trace 的延遲，也不能用兩輪差異宣稱演算法加速。較早的 31 筆縮放 UI 觀察為 P50 50.2 ms、P95 74.6 ms；增加 JSON 原始時間樣本後的一輪為縮放 P95 51.5 ms、平移 65.0 ms。補上背景切換時清除在途觀測後，再取得表中的最終量測；保留差異而不把單輪結果視為穩定上界。

長任務使用 [W3C Long Tasks API](https://www.w3.org/TR/longtasks-1/) 的主頁觀測；本輪沒有觀測到 ≥50 ms 任務，並非證明整個瀏覽器沒有長任務。JS heap 使用瀏覽器可選的 performance.memory；[此 API 可能忽略 Worker heap 或計入共用 heap](https://developer.mozilla.org/en-US/docs/Web/API/Performance/memory)，因此只標成近似抽樣，不當作完整瀏覽器的峰值 RAM。本輪主頁抽樣約數十 MB，不涵蓋 Worker、原生／GPU 或磁碟頁面快取。

v0.8.0 的 core.js／relations.js 未修改，仍由測試核對 v0.7.1 引擎與百萬 counter 的來源雜湊。上述瀏覽器更新量測與既有 Node 匯入基準分開，沒有重標舊解析秒數。

v0.7.2 僅調整詳情面板的空間分配；解析／索引／關聯核心與 v0.7.1 來源雜湊相同，沿用下列基準。面板高度修正以瀏覽器幾何與實際鍵盤操作另行驗收。

## v0.7.1 引擎

新增從既有索引解析 B/E 完整區段與 counter 樣本的按需查找；不建立整份 offset 對照表，不修改磁碟格式。以最終核心重新量測同規格 3 GB：建索引 42.90 秒、程序 RSS 峰值 339.46 MB，冷應用快取中位數／P95 為 6.25／59.32 ms，熱快取為 4.49／53.78 ms，位址查找 1.27 ms。完整來源雜湊與數據見 [v0.7.1 引擎紀錄](benchmark-2026-10-29-v0.7.1.json)。

同源百萬筆 counter：5.25 秒，程序 RSS 峰值 356.64 MB；80 個視窗的極值全部符合原始數據，冷查詢中位數／P95 為 9.66／21.66 ms，熱查詢為 8.83／20.98 ms。[v0.7.1 曲線紀錄](counter-benchmark-2026-10-29-v0.7.1.json)。兩份均為 Node Worker 與檔案系統替身，不能當作瀏覽器峰值記憶體或畫面效能。單次量測受快取與系統負載影響，不據此宣稱加速。

B/E 與 counter 的實際關聯跳轉另在瀏覽器核對時長、端點 Args、去重與數值；既有 3 GB 瀏覽器 File／OPFS／tar 實測保留於下方 v0.7.0 紀錄。未重新把舊瀏覽器秒數標成 v0.7.1 的量測。

## v0.7.0

連線候選改為明確 Flow／define-use 優先後，重新量測同規格 3,000,583,032 bytes、2,932,637 筆 X 事件。Node 引擎：建索引 45.73 秒，RSS 峰值 347.71 MB；80 次查詢的冷應用快取中位數／P95 為 6.36／67.29 ms，熱快取為 4.60／60.39 ms；位址查詢 1.38 ms、14 個候選。主程序計時器額外延遲最大 22.33 ms。OS 頁面快取未清除，同時有瀏覽器工作負載，不將跨時次差異宣稱為效能提升。[原始數據與來源雜湊](benchmark-2026-10-29-v0.7.0.json)。counter 核心未變，沿用下方 v0.4.0 專項紀錄並由測試核對核心雜湊。

Windows 內嵌 Chromium 156 亦已經由實際選檔操作，測試同一份實體 3 GB JSON 的 File.stream／OPFS：畫面回報 41.21 秒、2,932,637 筆；全覽查詢一次為 8.5 ms／5,808 節點。重新整理後從本機索引還原，不重新解析；晚期約 129 秒位置放大到微秒範圍，查詢一次為 3.4 ms／2 節點。以上是離散 UI 觀察，並非 p95、FPS、瀏覽器峰值記憶體或任意真實 trace 的保證。

另以 59,310,386 bytes 的 tar.gz（內含同一份 3 GB JSON）測試串流解壓與索引，初次成員解析為 45.94 秒、整包 46.03 秒，事件數相同；其後修正取消流程，最終版本複驗結果見[驗證紀錄](VERIFICATION.md)。分析期間實測視窗查詢可繼續，取消 Args 分析後保留 Trace；小檔索引直接切換、大檔本機還原皆經 UI 驗證。測試資料均為可重建的合成資料，沒有使用或公開使用者內部 trace。

## 歷史基準與方法

v0.5.0 增加多檔切換、索引快取與同 TfliteID 比較，`core.js`／`relations.js` 與下列 v0.4.0 基準來源完全相同，沿用既有量測並由測試核對 SHA-256。此基準不涵蓋多份索引同時保留的記憶體或跨檔 Args 全掃描成本；這些仍需真實瀏覽器驗收。

v0.6.0 增加三版本全圖／算子比較、獨立時間窗與切換穩定性修正。引擎來源仍相同，沿用上述基準；新增的 Args 彙整與 Worker 生命週期行為由對應測試驗證，並不以 3 GB 建索引秒數代表比較速度。

2026-10-29，v0.4.0 重新測試同一份 `dist/core.js`、`dist/relations.js`，以 Node Worker 與真實檔案系統介面替換瀏覽器 OPFS。這驗證解析／索引的演算法與磁碟讀寫路徑，**沒有驗證瀏覽器 OPFS、File.stream、gzip 或 Canvas 的時間、記憶體、FPS**。

| 事件 | 2,932,637 筆 X 事件、8 軌道 |
| Args 分布 | 每事件約 900 bytes 字串，另有索引欄位；每 25 筆帶 address |
| 輸入順序 | 依 ts 遞增；合成資料，非使用者真實 trace |
| 關聯鍵 | 117,306 筆 |

| 吞吐量 | 73.79 MB/s（含合成輸入生成成本） |
| 程序 RSS 峰值 | 344.17 MB（主程序與 Worker 合計，非瀏覽器記憶體） |
| 索引與事件磁碟量 | 3,190,031,386 bytes |

查詢共 80 個視窗、每次 8 軌道、寬度 1,200 像素，交錯全範圍、1/10、1/100、1/1000 範圍。冷查詢清除應用層的 24 塊讀取快取，**未清除 OS 頁面快取**。P95 為排序後第 floor((N−1)×0.95) 個數值。

硬體：Intel Core i5-10400 2.90 GHz、12 邏輯 CPU、34.24 GB OS 回報 RAM；Windows x64，Node v24.22.1。磁碟介面使用同步檔案 I/O，測試檔在系統暫存資料夾；磁碟型號未記錄。

原始數據與受測來源 SHA-256：[benchmark-2026-10-29-v0.4.0.json](benchmark-2026-10-29-v0.4.0.json)。腳本：[benchmark.mjs](../scripts/benchmark.mjs)。如解析器或索引改變，必須檢查雜湊與重跑受影響的基準，不能以版本號當作相同來源的證明。

未涵蓋：高密度微小事件、每事件唯一名稱、大量軌道、巨型單筆 args、完全逆序事件、大量位址鍵、gzip 解壓縮、真實瀏覽器儲存配額及渲染。這些形狀可能有顯著不同的效能，初版不把單次合成測試宣稱為「任意 3 GB trace 都快速」或「快於 Perfetto」。

下一輪瀏覽器驗收應在桌面 Chrome / Edge 以同一來源 commit 量測首次匯入、快取還原、峰值記憶體、平移／縮放 p50/p95 延遲、長任務與 address 查詢，並使用實際 trace。

初版紀錄仍保留於 [benchmark-2026-10-29.json](benchmark-2026-10-29.json)。v0.2.1 未命名事件補名的紀錄也保留於 [benchmark-2026-10-29-v0.2.1.json](benchmark-2026-10-29-v0.2.1.json)。本次 v0.4.0 加入短 TID 補名與 Args 分析，修正末端點樣本的半開範圍，再次量測匯入與查詢，但仍不是瀏覽器實測。單次查詢延遲會受 OS 快取與系統負載影響，不以不同時次的單一結果宣稱效能提升。

## 100 萬筆 counter 專項

同一環境、同一份 v0.4.0 核心，另產生 1,000,000 筆 C 事件、4 條數值曲線，JSON 共 94,702,287 bytes。一般值是小於 1 的連續變動，定期加入正／負 12,345 尖峰。80 個查詢交錯全範圍、1/10、1/100、1/1000，寬度 1,200 畫素；每個查詢的最大與最小值都與原始數據重新計算核對。

| 項目 | 結果 |
| --- | --- |
| 解析＋索引＋fsync | 5.31 秒 |
| 程序 RSS 峰值（採樣） | 356.80 MB |
| 事件及固定寬度索引 | 157,702,286 bytes |
| Manifest | 2,998,402 bytes |
| 冷應用快取查詢 | 中位數 10.08 ms，P95 18.37 ms |
| 熱應用快取查詢 | 中位數 9.91 ms，P95 21.16 ms |
| 最大傳回節點數（4 軌道合計） | 18,593 |
| 範圍極值核對 | 80／80 符合 |

摘要每個索引區塊至多 32 個時間桶，各保留首尾與最大／最小樣本，以緊湊數字 tuple 儲存。僅在摘要時間跨度不大於一個畫素、且完全落在視窗內時使用摘要；跨視窗邊界與放大後讀取確切索引。最終每條軌道每畫素最多四個代表樣本，並可額外回傳左右各一個相鄰樣本作為繪圖裁切脈絡，不把插值當作事件。輸出仍是解析度聚合，不能視為每筆樣本都有獨立像素；放大可查看原始資料。

粗摘要不回報虛構的精確每畫素樣本數。原始索引的逐筆讀取使用固定暫存槽，避免因一個視窗建立百萬個完整物件。這是 Node 引擎的 counter 測試，輸入約 95 MB，**不是 3 GB counter 或瀏覽器的驗收**；RSS 包含測試主程序與 Worker，不是瀏覽器記憶體。

原始數據：[counter-benchmark-2026-10-29-v0.4.0.json](counter-benchmark-2026-10-29-v0.4.0.json)。重播：`node scripts/benchmark-counters.mjs 1000000`。輸入與索引檔在系統暫存目錄產生，完成後移除；只保留數據紀錄。
